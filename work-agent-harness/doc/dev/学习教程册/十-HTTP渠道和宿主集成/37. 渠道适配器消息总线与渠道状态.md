# 第 37 章｜渠道适配器、消息总线与渠道状态

> 所属篇：HTTP、渠道和宿主集成
> 功能范围：`WAH-API-005–007、WAH-AUTO-005`
> 导航：[教程册总目录](../README.md) · [本篇导读](README.md) · [课程索引](../../学习手册/课程目录.md) · [功能路线](../../学习手册/功能单元路线.md) · [唯一状态清单](../../学习手册/功能清单.md)

> **本章定位：设计文档，不实现代码。**
>
> **先说事实，避免读者白找**：原版 `evoflow` 包里**没有**"渠道适配器 + 消息总线 + 渠道状态"这套模块。
> `grep -rln "channel_adapter\|ChannelAdapter\|MessageBus"` 只命中无关文件；`feishu` / `wecom` 只出现在 `proactive/feishu_notify.py`、`proactive/feishu_binding.py`、`proactive/wecom_binding.py`（**主动任务推送**）和少量工具里。
> 也就是说：**双向渠道（用户发消息进来 → Agent 回复出去）不在本仓实现**。本章是按"如果要接，需要什么"来写的设计章，不是仿写章。

## 场景

用户不只在一个地方用 Agent：网页、飞书群、企业微信、桌面客户端。

每个渠道都有自己的脾气：

- 飞书要 access_token，token 两小时过期；
- 企微有 IP 白名单；
- 网页要 SSE，飞书要回调；
- 飞书发消息有频率限制（超了会被封）。

如果每个渠道各写一套，最后会有四份几乎一样、但各有一处不同的代码。所以标准做法是：**统一消息总线 + 渠道适配器**。

## 本章要完成的功能

| 功能 ID | 要达成的行为 | 用户可见结果 |
|---|---|---|
| `WAH-API-005` | 渠道适配器：统一入站/出站接口 | 加渠道不改主逻辑 |
| `WAH-API-006` | 消息总线：入站消息归一到统一格式 | 不管从哪来，Agent 看到的是同一种消息 |
| `WAH-API-007` | 渠道状态：token/限流/健康 | 渠道断了能看出来 |
| `WAH-AUTO-005` | 出站投递（与第 30 章打通） | 主动任务能推到渠道 |

## 本节业务问题

| 问题 | 后果 |
|---|---|
| 渠道各写一套 | 四份代码，改一处漏三处 |
| 入站不归一 | Agent 要处理四种消息格式 |
| token 不管理 | 两小时后全部 401 |
| 不限流 | 触发平台封禁 |
| 无健康状态 | 渠道静默失败，没人知道 |
| 出站无重试 | 网络抖动就丢消息 |
| 消息 ID 不幂等 | 平台重推时重复处理 |

## EvoFlow 源码阅读路径

**原版真实存在的只有"出站推送"这一半**：

| 层 | 文件与真实符号 | 作用 |
|---|---|---|
| ① 渠道选择 | `proactive/feishu_notify.py:34` `_approval_channels(role)` | 该角色走哪些渠道 |
| ② 退订 | `:39` `_feishu_channel_not_opted_out(role)` | 退订不推 |
| ③ 目标解析 | `:51` `_outbound_feishu_target(role)`；`:75` `resolve_role_feishu_target(role)`；`:65` `_send_account_for_target(role, receive_id, receive_id_type)` | 发给谁、用哪个账号 |
| ④ 绑定持久化 | `proactive/feishu_binding.py`、`proactive/wecom_binding.py`、`proactive/push_binding_repo.py` | 绑定关系 |
| ⑤ 推送策略 | `proactive/push_policy.py` | 什么时候推 |
| ⑥ 排障 | `proactive/diagnose_feishu_push.py` | **专门的推送诊断脚本**（说明这块踩过坑） |

**不存在的部分**：`ChannelAdapter` 抽象、`MessageBus`、渠道健康状态表、入站 webhook 处理。这四样本章按设计写。

逐层追读要点：`diagnose_feishu_push` 单独成文件，说明"推送失败排查"是真实的高频问题；`_send_account_for_target` 有账号维度，说明一个组织可能有多个发送账号。

## 调用流程（设计稿）

```text
入站：飞书回调 / 网页 POST
  ▼
① 适配器解析    ChannelAdapter.parse(raw) → UnifiedMessage
  ▼
② 归一          统一字段：channel / user_id / thread_id / text / msg_id
  ▼
③ 幂等          按 msg_id 去重（平台会重推）
  ▼
④ 进总线        MessageBus.publish(UnifiedMessage)
  ▼
⑤ 跑 Agent      （第 35 章的聊天 API）
  ▼
⑥ 出站          ChannelAdapter.send(thread_id, text)
  │                ├ token 失效 → 刷新
  │                └ 限流 → 退避重试
  ▼
⑦ 状态          记录渠道健康（最后成功时间 / 失败原因）
```

## WorkAgentHarness 现状与设计

**现状**：只有 CLI。没有任何渠道。

| 缺口 | 设计方案 | 边界 |
|---|---|---|
| 适配器 | `class Channel(ABC)`：`parse(raw)` / `send(text)` | 只做一个：`WebhookChannel`（纯 HTTP） |
| 归一 | `UnifiedMessage(channel, user_id, thread_id, text, msg_id)` | 五字段 |
| 幂等 | `processed_messages(msg_id)` 表，重复即丢 | 对齐平台重推 |
| 总线 | **不做**：单渠道直接函数调用 | 无多渠道路由 |
| 限流 | 简单计数（每分钟 20 条） | 不做令牌桶 |
| 健康 | `channel_health(channel, last_ok_at, last_error)` | 单表 |
| 飞书/企微 | **不做** | 无 SDK、无 OAuth |
| 出站重试 | 3 次指数退避 | 对齐思路 |

**必须写清**：本章**没有可仿写的原版**。写它的价值是让读者知道"接渠道真正的工作量在哪"（token、限流、幂等、健康），而不是让读者以为这是抄来的。

## 与 EvoFlow 的差异

| 项 | EvoFlow | 本项目 |
|---|---|---|
| 入站渠道 | **不在此仓实现** | 一个 HTTP webhook |
| 出站推送 | 飞书 + 企微（`proactive/`） | webhook |
| 渠道抽象 | 无 `ChannelAdapter` | 自造 `Channel` 抽象 |
| 消息总线 | 无 | 不做 |
| 幂等 | 未核实到 | `processed_messages` |
| 健康状态 | 有诊断脚本 | `channel_health` |
| 限流 | 平台侧 | 本地简单计数 |
