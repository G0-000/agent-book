## 四、分阶段执行卡

每张卡固定五段：先写什么、L1/L2/L3/L4 各做到哪、验收证据、常见坑。详细源码入口和调用链以对应章节为准。

### S0｜基线与骨架（第 1–2 章）

**先写什么**

- `backend/packages/harness/workagentharness/` 下建包骨架：`config/`、`models/`、`agents/`、`persistence/`、`execution/`、`tools/`、`middleware/`、`context/`、`memory/`、`events/`、`cli/`、`app_server/`。
- 一个 `config.yaml` fixture，只放一个 agent、一个 fake provider。
- 一份 `tests/chapters/` 目录，按章建测试文件。

**L1–L4**

- L1：空壳启动，能打印配置加载结果。
- L2：配置来源（YAML/env/默认值）与校验错误可读。
- L3：接真实 provider 配置，密钥脱敏。
- L4：缺字段、非法路径、坏 YAML 各一条失败路径。

**验收证据**：三仓库 commit、许可三件、入口图、`python -m workagentharness.cli --help` 实测输出。

**坑**：把“目录建好了”当第一阶段完成；没冻结 sha 就开始追源码。

### S1｜单轮可运行（第 2 篇，3–7 章）

**先写什么**：`config` → `models`（factory/resolver/credential）→ `agents/lead_agent` → `persistence`（session/message/run）→ `execution`（Run 生命周期）→ `cli` / `app_server`。

**L1–L4**

- L1：fake 模型，输入一句返回一句；thread 内两轮可延续。
- L2：真实入口（CLI 或 stdio RPC）进来；消息/会话落 SQLite；Checkpoint 可保存与恢复。
- L3：多 thread 隔离、并发轮次、取消传播、分享/归档等适用变体。
- L4：缺凭证、模型超时、重复请求、重启后续跑、checkpoint 版本不兼容。

**验收证据**：`运行命令 + 预期 + 实测 + 依赖真假`；重启前后同一 thread 的消息序列。

**坑**：只在 pytest 里调函数，不算真实入口；把内存 buffer 补发当持久化恢复。

### S2｜工具与流式（第 3 篇，8–13 章）

**先写什么**：`tools/catalog` → `tools/result` → `tools/builtins`（calculator、workspace_file）→ `tools/host_direct`（终端/文件边界）→ `middleware`（工具审计）→ `events`（token/tool/end 事件）。

**L1–L4**

- L1：注册一个纯函数工具，模型能发现并调用；结果结构化返回。
- L2：工具注入真实 agent；结果进消息流；SSE 客户端能消费 token 与工具事件。
- L3：文件/终端工具接真实 workspace；大结果裁剪/外存；后台命令轮询与终止；Browser/CUA 用 fake adapter。
- L4：参数类型错、工具超时、取消、越权路径、断流重连、输出截断边界。

**验收证据**：一条含工具调用的完整 SSE 事件序列（含关联 ID 与结束事件）；一条失败工具的错误规范化结果。

**坑**：把工具函数存在当“模型会用工具”；SSE 只测 happy path，没测断流恢复。

### S3｜上下文与记忆（第 4 篇，14–18 章）

**先写什么**：`context/`（来源、预算、压缩）→ `memory/`（短期 recall、长期存储、巩固、注入）→ `assets/`（资产/产物/事项）→ 反思结果落地。

**L1–L4**

- L1：固定 token budget 下组装系统提示 + 当前输入 + 一段历史；能触发一次压缩。
- L2：压缩后能恢复最新轮次；长期记忆写入后可召回；注入带来源标识。
- L3：记忆巩固/知识图谱抽取（fixture 多条合并一条）、资产生命周期、namespace 隔离。
- L4：超预算边界、压缩失败回退、记忆冲突、权限与清除路径。

**验收证据**：压缩前后 token 与消息序列对照；跨会话召回记录；注入后的完整 prompt 片段。

**坑**：把“摘要生成了”当“能恢复”；不测压缩后最新轮次是否丢失。

### S4｜知识与工作空间（第 5 篇，19–23 章，设计态）

> 第 19–23 章当前无实现代码，先做理解验收和“本章实作单”，转入实现时再按 L1→L4 执行。

**先写什么**：新增 `knowledge/`（上传、解析、切块、embedding、检索、引用）、`workspace/`（代码索引、符号上下文）。

**最小闭环建议**

- L1：上传一份 md → 切块 → 内存向量检索 → 返回带引用的答案。
- L2：换持久化向量存储；引用能回到原文位置。
- L3：Owned Knowledge 与知识地图；代码索引进符号表。
- L4：坏文件、空文档、超大文件、检索无结果、引用越界。

**验收证据**：上传→提问→命中的 chunk 与引用原文；索引构建耗时与条目数。

**坑**：检索“看起来相关”就算命中；引用没有原文定位。

### S5｜委派与治理（第 6 篇，24–27 章）

**先写什么**：子代理注册/选择/结果汇总 → 沙箱与宿主执行 → 会话工具绑定、审批、取消与清理。

**L1–L4**

- L1：主 Agent 委派一个子任务给子代理，拿回结构化结果。
- L2：子代理有独立上下文与工具集；执行在受控 workspace 内。
- L3：审批流、工具绑定范围、取消传播、会话结束清理。
- L4：越权工具、审批拒绝、子代理超时、并发委派冲突。

**验收证据**：委派调用链与子代理输出；一次被拒绝的危险操作记录（含拒绝原因）。

**坑**：默认放行且没验证拒绝路径；子代理共享主上下文导致状态污染。

### S6｜计划与自动化（第 7–8 篇，28–38 章）

**先写什么**：`plan/`（Plan 解析、Goal 图）→ 协作账本/任务中心 → Workflow/App 输入 → 探索预算 → 暂停恢复幂等 → `automation/`（定义、调度器、心跳、通知）。

**L1–L4**

- L1：解析一份 Plan，生成 Goal 节点并顺序执行两个步骤。
- L2：状态持久化；暂停后能恢复且不重复执行（幂等键）。
- L3：协作分工、任务中心、策略路由、定时规则与重启补偿。
- L4：重复触发、错过的调度窗口、取消中的任务、通知失败重试。

**验收证据**：同一任务执行两次的结果一致性；暂停/恢复前后状态快照；调度器触发日志。

**坑**：把“能暂停”当“能恢复”；没有幂等键就重跑。

### S7｜外部生态（第 9 篇，39–43 章）

**先写什么**：`mcp/`（连接、发现、调用、OAuth）→ 插件扩展壳与 Capability 授权 → Skills 加载/资源 → 外部 Agent Adapter 与 A2A。

**L1–L4**

- L1：连一个本地 MCP server，列工具并调用一次。
- L2：工具 schema 映射进 catalog；授权范围生效。
- L3：OAuth 流程、插件桥接、Skills 资源发现。
- L4：连接失败、token 过期、工具消失、授权越界、超时。

**验收证据**：MCP 握手与一次调用往返；授权拒绝记录。

**坑**：把 MCP 工具直接透传给模型，没做 schema 与权限映射。

### S8｜渠道与产品面（第 10–12 篇，44–59 章）

**先写什么**：`app_server`/Gateway（HTTP、SSE）→ 兼容协议与代理 → 渠道适配器与消息总线 → `authz`（Principal/ACL/JWT/OIDC）→ 观测（trace/日志/成本）→ Eval → 人格内核 → Web/桌面入口。

**L1–L4**

- L1：HTTP 起一个聊天接口，返回一条回复。
- L2：SSE 流式；身份主体进入；聊天记录可分页。
- L3：渠道收发、兼容协议、观测埋点、Eval 回归。
- L4：未授权、token 过期、渠道断连、限流、成本超限。

**验收证据**：`curl` 请求与响应；一次鉴权失败；一条 trace 的完整 span。

**坑**：先做 UI 再做入口；权限只测放行。

### S9｜全量收口（第 13 篇，60 章）

选一条真实用户任务，从入口走到产物、恢复和通知，贯穿 S1–S8 的功能域。只写“各模块都做了”不算通过，必须有一条端到端记录。

## 五、每一步都照这个动作做

1. 写清用户、入口、输入、可见结果、权限主体、涉及状态。
2. 追 EvoFlow 链路：入口/注册 → 调用者 → 核心行为 → 持久化/外部依赖 → 返回事件。
3. 画现状图：只画源码证实的关系；找不到调用者的标“待追入口”。
4. 做 L1：fake 模型/内存库/fixture，跑通一条成功路径。
5. 补 L2–L4：真实入口与持久化、功能变体、失败/权限/并发/取消/恢复。
6. 对照 AgentFlow：记录当时做到什么、哪里误判。
7. 写回功能清单：ID、三仓库 commit、路径/符号、运行命令、预期、实测、差异、日期。

## 六、验收口径（别自创）

- **四类核验**：真实入口、成功与失败边界、状态与恢复、权限与隔离；“代码存在”≠“入口接线”≠“边界验收”。
- **两类方法**：理解验收（路径/符号、调用链图、讲解）与运行验收（命令/入口 + 预期 + 实测 + 依赖真假）。读懂不能替代跑通。
- **三级验收**：节级（每章末节）、篇级（每篇末章）、项目级（第 60 章）。
- **替身规则**：拿不到真实条件（API Key、IM 租户、桌面环境）用 fake/本地替身验，标 `已验收（替身）` 并写“真实服务未验证”；**不许因此排除**。
- **排除规则**：只有确认不属于仿写目标才可排除，且写清缺什么、影响什么、为什么不做、有无更弱替代。

## 八、常见坑

1. **拿 HEAD 当教材**：验收前必须确认按 `8e462a37` 检出；EvoFlow 更新另起一轮。
2. **按模块平铺**：先有用户行为再建模块；否则做出一堆“存在但没接线”的组件。
3. **跳过失败路径**：只跑 happy path 的章节不算通过。
4. **mock 当真实**：结论里必须写依赖真伪，mock 通过只能记 `已验收（替身）`。
5. **状态表分裂**：不要在学习记录里另造状态；只写功能清单。
6. **追求全量再收口**：同一条功能 ID 未走完 L1–L4 就开下一个，最后全是半成品。
7. **忽略许可**：不要把受限源码整段搬进实现仓。
8. **第 19–60 章写成“已实现”**：设计态章节只能交理解验收和实作单。
