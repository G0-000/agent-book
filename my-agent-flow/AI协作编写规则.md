# EvoFlow 仿写项目：AI 协作编写规则

> 本规则适用于所有参与本项目的 AI。开始编辑文档或代码前先读本文件，并阅读当前章节与其引用的 EvoFlow 源码。

## 1. 项目目标与文档分工

- 本项目是按章节学习并仿写 EvoFlow，不是一次性实现完整产品，也不是只写概念介绍。
- `agent-book/public/EvoFlow-学习规划-总文档.md` 是便于阅读和交接的单文件合订本，由拆分文档生成，禁止直接编辑。
- `agent-book/my-agent-flow/` 是拆分文档与合订本的唯一来源。正文修改在本目录完成，再运行 `python3 scripts/build_evoflow_master.py` 更新 `public/` 下的合订本。
- 仿写代码在代码仓库 `my-agent-flow/backend/`。章节说明的文件路径应与 EvoFlow 对应模块尽量同构，具体实现按本项目当前阶段逐步增加。
- 遇到总文档、拆分文档、代码、EvoFlow 源码不一致时，不要自行猜测或悄悄改写；先核对来源和当前版本，在拆分正文中修正并记录差异，再重建合订本。

## 2. 学习与实现顺序

- 严格沿既定章节顺序推进：先打通最小闭环，再逐章增加持久化、工具、上下文、记忆及后续能力，最终达到全功能集成验收。
- 当前章节只实现本章目标和后续章节明确依赖的最小接口。后续功能、未来扩展、与当前闭环无关的抽象，不提前实现。
- 代码量服从章节目标：EvoFlow 当前功能需要多少、本章要学习多少，就实现多少。不可为“看起来完整”提前创建一批空文件、空类、占位接口或臆造模块。
- 每章在写代码前说明本阶段闭环、输入输出、依赖的前置章节、EvoFlow 对照文件以及本阶段暂不涉及的后续能力。
- 推荐递进：L1 最小可运行闭环 → L2 接入真实调用入口 → L3 补齐本章核心功能 → L4 处理失败边界。仅在章节目标需要时使用各层，不为层级本身扩展范围。
- 前置章节的验收未通过时，不把依赖该能力的后续功能伪装成已完成；可以记录阻塞和继续做不依赖它的工作。

## 3. 每个技术章节的内容要求

每章围绕一个可验证的行为组织，并包含以下内容（标题可因内容调整，信息不可缺失）：

1. **目标与范围**：读完能实现什么，明确当前阶段边界。
2. **前置知识与依赖**：解释所需概念，指出依赖的前章产物。
3. **EvoFlow 源码导读**：给出真实路径、符号名和阅读顺序；行号仅在已核实且稳定时引用。
4. **调用逻辑**：说明入口、关键调用节点、状态/数据如何传递、出口和失败/中断点；用图时保证与正文和源码一致。
5. **实现步骤**：按实际开发顺序逐步说明目标文件、职责、关键逻辑、为什么这样组织，以及可直接运行的代码或明确的代码变更。
6. **知识点讲解**：讲清本节用到的原理，并说明它在当前实现的哪一步发挥作用。
7. **EvoFlow 对照与差异**：按**文件级**列映射表（EvoFlow 文件 → 本项目文件 → 本章实现的函数/字段 → 未实现部分），标明借鉴的结构/行为、本项目有意省略的部分及原因；不能把推测写成源码事实，也不能只写“参考了 persistence”。
8. **逐步验收与排错**：每个重要步骤有相应验证；给出命令、预期结果和常见失败的定位办法。
9. **章节完成标准**：用可观察行为和验收结果定义“完成”，并更新进度台账。

## 4. 代码对齐规则

- 先查真实 EvoFlow 源码再写实现；核实模块路径、类/函数职责、调用方向、状态/数据结构和边界行为。路径相似不代表行为相同。
- 本项目代码按 EvoFlow 的模块职责和目录结构对齐，采用独立实现；不整段复制 EvoFlow 代码。对齐结构不等于为了未来功能复刻整个目录。
- 只创建当前阶段实际需要的文件。若本章需要的职责在现有文件中，先判断是否应延续该文件；不要仅为对齐文件名而制造空文件。
- 新增/改动每个文件都要能对应到章节步骤和当前行为。说明谁调用它、它调用谁、输入输出是什么。避免无调用者的死代码、重复抽象和“以后再用”的预留实现。
- 先保留最小接口，需求出现后再扩展。不可把未来可能的多租户、插件、队列、协议兼容等功能提前塞进当前闭环。

### 4.1 文件映射硬规则（不可协商）

- **一个 EvoFlow 源文件 → 本项目一个同名文件**。禁止把 EvoFlow 的两个文件合并成一个，禁止把多个职责塞进一个类。例：`persistence/chat_message_repositories.py`（消息）与 `persistence/session_repositories.py`（会话）必须各自存在，不得合并为 `persistence/messages.py`。
- **禁止自造聚合层**：不得为了“教学方便”引入 EvoFlow 没有的 `Store`、`Manager`、`Service` 类，把若干仓储函数包起来。EvoFlow 是函数式仓储就写函数式仓储。
- **符号名照抄**：函数名、类名、字段名、表名以 EvoFlow 源码为准；只允许删减（本章用不到的字段/分支不实现），不允许改名、不允许新增同类语义的别名。
- **按需抄，不预抄**：当前章节用多少抄多少；后续章节需要时再补对应文件/字段，不得提前铺空文件。
- **拆文件即拆测试**：文件拆成几个，测试就覆盖几个入口；合并版留下的类名、测试名、文档叙述必须全局搜一遍改净（`grep -rn`）。
- **提交前自检**：`ls` 对照 EvoFlow 同目录文件清单，逐个确认本项目是否有同名对应文件或明确记录“本章不需要”；同名文件缺失且无记录，视为不合规。
### 4.2 模块头注释三段式（每个 .py 必写）

顶部 docstring 固定三段，顺序不变：

```python
"""一、文件说明
    这个文件负责什么、为什么这样切（一到三句）。

二、目录结构
    packages/harness/myagentflow/persistence/
    ├── db.py                          ← 本文件：连接、锁、建表
    ├── session_repositories.py        sessions 表
    └── chat_message_repositories.py   chat_messages 表

三、关键方法
    get_db()                取共享连接；首次调用建目录、开 WAL、建表
    reset_db()              关闭并丢弃连接；测试换库用
"""
```

- 一：只讲职责与取舍，不复述下面代码；
- 二：画出本文件所在目录，兄弟文件各一句话，本文件标 `← 本文件`；
- 三：每个公开函数/类一行，写「做什么」，不写「对齐 EvoFlow 某行」这类出处；
- 批量维护用 `backend/tools/file_headers.py`（`--force` 重建）；新增文件后跑一次，缺段即不合规。

### 4.3 测试代码注释（`tests/` 下每个文件必写）

- 文件头三段：一、文件说明（测哪一章、验证什么行为）/ 二、覆盖（每个测试符号一行，写它测什么）/ 三、运行（`uv run pytest tests/chapters/<file> -q`）。
- 每个 `test_*`、每个替身类（如 `EchoModel`、`ScriptedModel`）、每个辅助函数（如 `_b64`）都要 docstring，写「验证什么、期望什么」，禁止“测试一下”式空话。
- 断言背后的约束用行内注释点明（如「旧版本号认领必须被拒：防双领」）；时间相关一律显式传 `now`，不靠 `sleep` 凑。
- 新增测试文件同样套用；缺文件头或缺符号说明，视为不合规。

- 代码示例必须与仓库现状相容，路径、导入、配置字段和依赖须核对；不提供看似完整但不能运行的伪代码而不作标注。
- 安全、许可、密钥、持久化和并发等行为不得凭经验补造；以源码证据和本项目明确范围为准，差异需写明。

## 5. 事实、引用与进度标记

- 把内容区分为：**EvoFlow 已核实事实**、**本项目实现选择**、**尚待核实**。对推断明确标为推断。
- EvoFlow 版本或提交基准以规划文档和进度台账为准。发现基准变化，先记录新旧基准及影响范围，不静默混用路径、行号或行为。
- 源码引用必须能回到文件和符号；涉及关键行为时实际阅读实现及调用处。仅确认路径存在，不能标为行为已核实。
- 沿用台账定义的状态（✅ 已核对源码、📄 原文迁移、🔍 结构已核对、🟡 骨架待核对、⬜ 未开始），不可把“文档写了实现步骤”说成“代码已实现/已运行”。
- 只有实际执行了章节验收并观察到结果，才能标记该验收通过；没有运行就如实注明未运行。

## 6. 修改流程与交付说明

1. 确认修改属于总纲/拆分正文/仿写代码/进度台账中的哪一项。
2. 阅读当前章节、前置章节、相关源码与当前代码，先检查是否已有内容，避免重复或破坏既有设计。
3. 只修改完成当前目标所需的范围；涉及正文时修改 `agent-book/my-agent-flow/` 的拆分源文件，禁止手改生成的合订本。
4. 文档修改后重建合订本，并确认生成结果包含修改；代码变更按章节给出的验收方式验证。不要声称未执行的检查已经通过。
5. 同步更新必要的章节目录、进度台账、导航和代码路径，保证链接可用、状态一致。
6. 交付时简要列明改了哪些文件、依据什么 EvoFlow 结构、实现到哪一阶段、做过哪些验证及未验证项。

## 7. 禁止事项

- 不把合订本当成正文来源直接编辑。
- 不脱离 EvoFlow 真实代码，仅凭文件名或常识臆造调用关系、API、类名、字段和行为。
- 不合并 EvoFlow 的多个源文件，不自造聚合类/管理器来“简化”教学；文件边界照 EvoFlow 走。
- 不跳过最小闭环，直接铺开后续全部功能；不为了“完整”提前实现未来章节。
- 不把知识点、流程图、步骤、代码彼此割裂；图和示例必须反映本章实际实现。
- 不把占位符、伪代码、未运行代码或结构核对包装成可运行实现或通过验收。
- 不在没有依据时删除既有实现、改变章节边界、重排学习路线或引入与本章无关的依赖。
